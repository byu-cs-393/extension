# TA-mode dashboard design — 2026-05-13

Follow-up to [ux-locked-5-12-2026.md](ux-locked-5-12-2026.md). The locked UX doc framed TA mode as "same scroll, different actions" — after designing this in detail, that doesn't hold. TAs aren't doing weekly assignments themselves; their mental model is **roster-first, not week-first**. This doc captures the corrected design.

Pairs with [topic-exam-5-12-2026.md](topic-exam-5-12-2026.md) — the topic exams covered here are live per the 2026-05-13 decision.

**Status:** Design captured. **Implementation deferred to a later phase.** The biggest unresolved upstream question — whether the course will have two topic-exam types (performance + articulation) or stick with one — affects scheduling details below; this doc assumes two for completeness, but most of it works either way.

---

## Should there be a TA view at all?

**Yes — but the minimum is small.**

What forces a TA interface to exist: topic-exam signoff. The TA has to confirm pass/fail. That can't happen in the student's view; the TA needs their own surface. Keystroke playback is also most naturally a TA-facing viewer.

Beyond those two, everything else is a productivity layer over what email alerts + the student dashboard already provide. The dashboard saves real TA time, but its absence wouldn't kill the course.

---

## Signoff: notification-approve, no PIN

When a student arrives at their booked slot and demonstrates the problem, the flow at the end of the session is:

1. Student clicks `[ Request signoff ]` on their dashboard.
2. A notification fires on the TA's device (browser notification + in-app prompt).
3. TA reviews the request in a detail view — student name, problem, session metrics (paste count, submit count, duration).
4. TA taps `[ ✓ Pass ]` or `[ ✗ Did not pass — let them retry ]`.

**No PIN.** The TA's authenticated session is the credential. Pattern is similar to a 2FA push prompt.

**Reflexive-approval mitigation:** the approve action is 2-step (notification → detail view → approve), not a single tap. The detail view shows the session metrics so the TA actually looks before confirming.

Sections:

- **Awaiting your approval** — sessions that just ended, waiting for the TA to confirm or reject. Notification-approve flow lives here. Acts as a fallback queue when notifications get missed (TA's device offline, notifications muted, etc.).
- **Today's schedule** — booked slots through the rest of the TA's day. Each row shows time, student, exam type, problem, and current state (done / upcoming / in-session).

Flag data (red / yellow / copy-paste) lives on a separate **Needs Attention page** accessed via the `[⚠ Attention]` header button — see below. This is intentional: the main dashboard is what's on screen when a student walks into the TA's office, and other students' flag status shouldn't be visible to passers-by.

## Scheduling

**All TA-student interactions are formally scheduled — no walk-up special case.** A student who wants to drop in spontaneously still books the slot (so it's marked taken and no one else grabs it). The TA's available calendar time *is* their office hours.

| Exam type | Slot length |
|---|---|
| Performance | 15 min |
| Articulation | 30 min |

(Subject to the unresolved "do we have one exam type or two?" decision from [topic-exam-5-12-2026.md](topic-exam-5-12-2026.md).)

The scheduling widget lives embedded in the student dashboard, so students never leave the extension to book.

### Implementation options (decision deferred)

The exact scheduling backend is intentionally deferred — the design above works with any of these:

| Option | Cost | Build | Multi-duration |
|---|---|---|---|
| Calendly Standard | ~$12/TA/month | None | ✓ Native |
| **Cal.com** (open-source — free hosted tier or self-host) | $0 | Account setup + embed | ✓ Native |
| Direct Google Calendar API integration | $0 | Build a custom scheduler UI on top of TA's gcal | ✓ Fully custom |
| Calendly free + manual double-booking for 30-min slots | $0 | Custom orchestration UI + edge-case handling | ⚠ Awkward UX |

**Lean:** Cal.com if free + native multi-duration is the priority. Calendly Standard if minimal build matters more than cost. Direct Google Calendar if BYU is already on Google Workspace and full UX control is worth the build.

### Required scheduler config (any backend)

- **Minimum booking notice = 0** (or ~5 min) so spontaneous drop-ins can grab a slot starting soon.
- **Multi-duration support** if there are two exam types.
- **Webhooks** to the extension's backend so it knows about new bookings, cancellations, and reschedules.

## MVP vs cuttable

| Element | Verdict | Why |
|---|---|---|
| Notification-approve signoff | **Required** | No other surface can complete signoff |
| Standalone keystroke replay viewer | **Required-ish** | Otherwise the copy-paste flag has nowhere to drill in to |
| "Awaiting approval" inbox | **MVP** | Holds requests that arrive when TA's device is offline / notifications missed |
| Today's schedule | **MVP** | TA needs to see what's coming; without this they'd be switching to their calendar app constantly |
| Needs Attention page (separate from main dashboard) | **MVP-lite** | Mirrors alert emails; useful if TAs work from the dashboard daily. Kept on its own page for privacy. |
| Student drill-in page | **MVP-lite** | Without it, "View" buttons go nowhere. Replays could be linked directly from emails as a v1 fallback. |
| Roster browse / stats tabs | **Cut for v1** | Build after real data tells you what's missing |

**Minimum viable scope:** notification-approve flow + replay viewer + today's schedule. Everything else is a productivity layer that can ship later.

## Open questions

- **Two exam types vs one.** Pending instructor discussion. Affects whether scheduling needs multi-duration support.
- **Scheduler backend choice.** Cal.com vs Calendly vs Google Calendar API — pick when implementation time approaches.
- **Multi-TA routing.** If multiple TAs are working a slot, who gets a given signoff notification? Student picks at booking time, or auto-routed?
- **No-shows.** Student books, doesn't arrive. TA marks no-show manually after a grace period? Auto-detected?
- **Cancellations.** Notify the TA so they know about the gap, or just free the slot silently?
- **Reminder cadence.** 24-hour email reminder before a booked slot? 1-hour? Both? Most schedulers handle this; direct-Google-Calendar would need it built.
